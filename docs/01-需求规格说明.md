## 1. 引言

### 1.1 目的与范围

本文档定义「HSP 微音游」在黄山派（SF32LB525UC6）开发板 + 1.85" 390×450 触摸屏上的需求。

- **本期（P0）做**：4 轨下落式节奏判定，无声节拍版——主界面 → 演奏 → 结算的完整闭环，加上可复现的性能/延迟自检输出。
- **P1 加**：从 TF 卡读谱面与播放 MP3 并与画面同步；命中时以**特殊音效**反馈（原定震动反馈，因马达需外购焊接且未采购而改为音效，见 ADR-0005）。
- **明确不做**：长按/滑动/多押/变速谱面、谱面编辑器、联网排行、多曲库管理、LVGL 界面框架。

### 1.2 术语与缩写

| 术语 | 含义 |
|---|---|
| 判定窗口 | 玩家点击时刻与音符应命中时刻的允许误差；超出即 Miss |
| 轨（Lane） | 屏幕上一列竖直下落通道；P0 为 4 轨 |
| 谱面（Chart） | 音符的「时间戳 + 轨号」数据集合；P0 随固件内置，P1 存 TF 卡 |
| 帧循环 | 固定周期执行「读输入 → 更新逻辑 → 绘制 → 提交」的主循环 |
| TE / VSYNC | 屏幕分帧同步信号；CO5300 支持，用于对齐刷帧避免撕裂 |
| PSRAM | 片外 8MB 高速内存（OPI，144MHz），用于帧缓冲 |
| Acc（准确率） | 按判定档位加权计算的命中率 |

## 2. 产品概述

### 2.1 一句话定位

一块口袋尺寸的简易音游（技术验证原型）：现在音游大多跑在手机、电脑和笨重的街机上，**没有专门为音游特化过的便携设备**；本项目用 4 轨下落 + 点到判定，验证 MCU 级硬件能不能撑起一次完整的节奏玩法，并把帧率与判定延迟变成可测量的数字，为以后可能出现的音游专用设备提供参考。

### 2.2 目标用户与使用场景

**先澄清一件事**：受开发板尺寸和交互条件限制，这板子上不会真有玩家长期玩音游。所以本产品**不做面向玩家的成品**，定位是技术验证原型。它的「用户」因此分两层：

- **本阶段的直接使用者**：作者本人（自测、调参、收集帧率与判定数据）和课程评审者（现场演示一局完整流程）。
- **未来的目标用户（不是本阶段要满足的对象）**：希望有一台便携、专为音游做的设备的玩家。本项目为这类设备的可行性探路。

- 典型场景 1：作者自测——上电、点「开始」，按节拍点按，串口同时输出帧率统计与判定延迟数据，用来判断参数是否合理。
- 典型场景 2：课程评审/答辩现场，当场演示一局完整流程（开始 → 演奏 → 结算）。

### 2.3 核心痛点与现有方案

现有音游几乎都落在三类设备上，**没人为音游单独做一台特化、能装进口袋的设备**：

| 现有形态 | 优点 | 不足（本项目关注的点） | 本产品的差异点 |
|---|---|---|---|
| 手机 / 平板音游 | 画面、曲库、手感成熟 | 通用设备，音游只是众多 App 之一，没有为音游特化；时序与延迟不对外暴露，测不了 | 专用硬件，帧率 / 判定延迟可打印、可复现 |
| PC 端音游 / 模拟器 | 开发调试方便 | 键盘大屏的交互，和「口袋里的触摸音游」不是一回事 | 竖向 4 轨 + 触摸判定 |
| 街机音游 | 体验与手感最好 | 昂贵、笨重、搬不动 | 口袋尺寸的 MCU 方案 |
| 现成开源嵌入式音游 | 做法可参考 | 与本板分辨率、触摸 IC 不匹配 | 针对 390×450 + FT6146 适配 |

**本项目的态度**：不打算替代上面任何一类，也**不做面向玩家的成品**；只回答一个问题——MCU 级硬件到底能不能做到"音符下落跟得上节奏、点到判定算得准"，并把答案变成一组可复现的数字，供未来的音游专用设备参考。

## 3. 功能需求

| 需求ID | 描述 | 优先级 | 验收标准 | 来源/场景 | 涉及硬件 | 状态 |
|---|---|---|---|---|---|---|
| REQ-001 | 上电进入主界面（显示曲名与「开始」），点击「开始」进入演奏状态 | P0 | 上电后 5s 内出现主界面；点击后 1s 内进入演奏，串口打印状态切换时间戳；录屏可见界面切换 | 场景1 | 屏幕、触摸 | 草稿 |
| REQ-002 | 4 轨音符从屏幕顶部向判定线匀速下落，位置随谱面时间戳连续变化 | P0 | 演奏 30s，串口逐帧记录帧间隔，**P95 ≤ 33ms（≥30fps）**；录屏中音符连续移动、无撕裂 | 场景1 | 屏幕、PSRAM | 草稿 |
| REQ-003 | 在判定线区域点按，按误差给出判定：**Perfect ≤ ±60ms、Good ≤ ±120ms、超出为 Miss**；一次点按最多消耗一个音符 | P0 | 以已知时刻输入 ≥50 次，判定结果与理论一致（串口日志比对）；判定延迟直方图 P95 ≤ 50ms（阈值待 M2 实测确认） | 场景1 | 触摸 | 草稿 |
| REQ-004 | Perfect/Good 使 Combo+1 并加分，Miss 使 Combo 归零；实时显示分数、Combo、Acc | P0 | 用「全 Perfect」与「故意漏点」各跑一遍，分数与 Acc 与手算一致（附串口输出与录屏） | 场景1 | 屏幕 | 草稿 |
| REQ-005 | 曲目结束后进入结算页，显示分数、最大 Combo、Acc、各判定计数；可重开一局 | P0 | 结束后 1s 内出现结算页，四项数据与过程日志一致；点「重开」回到演奏起始 | 场景1、2 | 屏幕、触摸 | 草稿 |
| REQ-006 | 谱面以文本表示（每行：`时间戳ms 轨号(0-3)`）；P0 一份内置谱面随固件烧录 | P0 | 解析失败有明确报错；串口打印解析摘要（音符数、末音符时间），与文件内容一致 | 场景1 | Flash | 草稿 |
| REQ-007 | 启动时输出**板上自检**：帧率统计、判定延迟直方图、谱面解析摘要，PASS/FAIL 明确 | P0 | 启动后串口输出三节自检；注入一次故意错误的谱面时，对应项输出 FAIL | 场景1 | 串口 | 草稿 |
| REQ-008 | 从 TF 卡加载谱面并播放 MP3，谱面时间轴**以音频播放进度为基准**同步 | P1 | 同一局同时录画面与音频，音符落线时刻与音频对应节拍偏差 ≤ 50ms（慢动作录屏 + 音频波形对齐） | 场景2 | TF 卡、喇叭 | 草稿 |
| REQ-009 | 命中音符时播放**特殊音效**反馈（可开关）——原定震动反馈，因马达需外购并焊接且未采购而改为音效（ADR-0005） | P1 | **客观判据**：命中时刻 GPIO 打点 / 串口打印音效触发时间戳，与判定时刻偏差 **≤ 20ms**；关闭开关后无音效 | 场景1 | 喇叭（NS4150B） | 草稿 |

优先级：P0 必须有；P1 应该有；P2 锦上添花。

## 4. 非功能需求

| 需求ID | 类别 | 描述 | 验收标准 |
|---|---|---|---|
| REQ-101 | 性能 | 演奏帧率 | 连续演奏 30s，帧间隔 P95 ≤ 33ms；无画面撕裂（TE 对齐） |
| REQ-102 | 资源 | 内存占用 | 帧缓冲 ≤ 2 帧（≈702KB，放 PSRAM）；打印大核 SRAM 静态占用并保留 ≥20% 余量 |
| REQ-103 | 可靠性 | 连续运行 | 连续演奏 10min 不死机；每 60s 打印 free heap，无持续下降趋势 |
| REQ-104 | 响应性 | 端到端延迟 | 触摸中断 → 画面反馈 ≤ 50ms（方法：GPIO 打点 + 串口时间戳；阈值 M2 实测后由学生确认） |
| REQ-105 | 合规 | 素材版权 | 仓库内音频/美术素材均为自制或明确免授权，附来源与许可；**不含 Phigros 等商业作品素材** |

> 非功能需求同样使用 `REQ-xxx` 编号并要在设计、测试中被覆盖（`check_trace.py` 会检查）。

## 5. 硬件约束与接口核对

> 对照黄山派能力核对，**不得依赖板子没有的能力**。

- [x] 屏幕：1.85" 390×450 触摸，QSPI（驱动 CO5300；**触摸 IC = FT6146**；**TE 信号可用**）—— 依据 `customer/boards/Kconfig_lcd` 的 `LCD_USING_TFT_CO5300` 与 `board.conf`
- [ ] 传感器：六轴 IMU（LSM6DS3TR-C）、三轴地磁（MMC5603NJ）、环境光（LTR-303ALS-01）—— **本项目不使用**（保留能力）
- [x] 音频：板载 MEMS 麦克风 + 喇叭（NS4150B 功放，喇叭接口）—— P1 用于播放
- [x] 无线：蓝牙 5.3；**无 WiFi** —— 本项目不使用
- [x] 交互：2 个按键（KEY1=PA34 / KEY2=PA43，高有效）、WS2812 RGB 灯（PA32）；**振动马达本项目不使用**（驱动电路在板上，但马达需外购焊接，REQ-009 已改为音效反馈，见 ADR-0005）
- [ ] 存储：TF 卡座（SPI1，FAT 文件系统）；**卡需自备**
- 需要额外采购的部件：**TF 卡**（P1 必需，存曲目与谱面）、**电池 GH1.25-2P**（官方 `mp3_sd_player` 例程注明本板长按按键检测需外接电池）。**不再采购振动马达**（REQ-009 已改为音效反馈，ADR-0005）

## 6. 我们考虑过但没有选择的方向

| 备选方向 | 没有选择的原因 | 谁做的判断 |
|---|---|---|
| 桌面计时/提醒终端（屏幕+按键+RGB） | 技术风险最低，但创新度不足，也体现不出触摸屏与实时时序能力 | 学生 |
| 穿戴姿态感知（IMU 抬腕亮屏 / 久坐提醒 / 计步） | 传感器板载可用，但需额外写姿态与计步算法，验证链条比"实时判定"更长 | 学生 |
| 蓝牙数据回传盒子（BT PAN / BLE） | `example/bt/pan` 的支持平台列表未含本板，还涉及手机侧配合与证书，不确定性最高 | 学生 |
| 全 LVGL 实现音游 | LVGL 例程 README 标注"未验证"；LVGL 动画不保证帧间隔，判定精度难保证 | agent 建议 + 学生确认 |

## 7. 假设与依赖

- 假设：屏幕实物与 SDK 配置一致（1.85" 390×450 / CO5300 / FT6146 / TE 可用）——需上板点亮后确认
- 假设：FT6146 的读点频率足以支撑 ±60ms 判定——**待 M2 实测验证**，若不足则需放宽判定窗口（走需求变更记录）
- 依赖：TF 卡、电池采购到货（P1 前置）
- 依赖：SDK 固定 v2.5.1，板型 `sf32lb52-lchspi-ulp`
- 约束：不得使用 Phigros 等商业作品的曲目、谱面、美术素材
- 约束：板载无 WiFi

## 8. 验收标准汇总

- [ ] 验收口径按 §2 的定位：以「作者 / 评审者能完整演示一局 + 数据可测量」为准，**不以消费者级可玩性为准**
- [ ] 全部 P0 需求（REQ-001~REQ-007）验收通过，结果记录在 `docs/04` 并有 `evidence/` 证据
- [ ] 非功能需求 REQ-101~REQ-105 均有可复现的测量记录
- [ ] P1 需求（REQ-008/REQ-009）完成，或如实标注"未执行"并说明原因
- [ ] 素材合规：仓库内无外部版权素材
