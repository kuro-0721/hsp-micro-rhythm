## 1. 执行摘要

- 测试时间范围：2026-10-10（M2 关键技术验证）。被测版本：探针 v1（分行刷，屏幕证据录制于 14:45:59）与探针 v2（BAND/FULL 对比，源码提交 `9346cd5`，构建产物 main.bin 301,180 B）
- 本轮不追求全量用例通过：M2 只回答"能不能做"的几个前置问题（屏幕能否点亮、帧率能否达标、触摸是否成为瓶颈）。已执行 4 项，其中 3 项完成、1 项未执行（判定窗口实际容差，需谱面与判定引擎）
- 结论：**M2 目标达成**——① 屏幕点亮正常（8 色带图案，390×450 与配置一致）；② 帧率经架构变更后达标（整屏单缓冲 p95 31ms ≤ 33ms，超时帧 0；分行刷 132ms 已被否决，见 ADR-0003）；③ 触摸"中断→读点"< 1ms，不是判定精度的瓶颈。**不构成功能放行**：全部 P0 功能需求（REQ-001~007）尚未实现，见第 7 节

## 8. 结论与建议

**M2「关键技术验证」**：屏幕能点亮且分辨率与配置一致、渲染帧率经架构调整后能满足 30fps、触摸链路延迟不构成瓶颈。

**M3「P0 功能」**：第 3 步完成后，**REQ-001~REQ-006 六个 P0 功能需求全部实现并通过上板验证**（TC-001~TC-006），首次拿到了完整的「主界面 → 演奏 → 结算 → 重开」闭环证据。判定、计分、Acc 三项在两局中均与手算完全一致（3150 / 54.31%、3350 / 57.75%）。

**关于帧率，此处必须写清一个容易被误读的点**：M3 前几轮的 `p95=33~34ms` 统计的是**每帧处理耗时**，不是帧间隔。收口轮修正统计口径后测得**真实帧间隔 avg=33ms / p95=34ms / max=38ms、掉帧 0**，按 CR-04 的 34ms 判据**恰好通过，但零余量**——每帧处理已占 31~32ms，距 33ms 目标只剩 1~2ms，其中 29ms 是等 VSYNC 的 flush（不可压缩）。

> 也就是说：**现在的结论是「刚好不超」，不是「有余地」。** 而且 11 分钟长跑后又紧了一点——work 由 31~32ms 涨到 **33ms**（flush 29→30ms），而目标帧间隔就是 33ms，意味着**帧循环已经没有任何 `rt_thread_delay` 余量，完全靠「刚好赶上」在跑**。若后续给音符加上长按条、特效或判定文字动画，这 0~2ms 大概率不够。报告不得将此表述为「帧率达标、余量充足」。

**但仍不构成完整的功能放行**，原因如下：

1. **REQ-104 只闭合了一半**：已测到「点击→状态切换 14/17ms」，但「触摸→画面实际翻转」的整链路仍未测。
2. **REQ-101 建在 1ms 分辨率的打点上**（R-10），34ms 这个数字本身带一档不确定度；且余量已降到 0~2ms（11 分钟长跑后 work=33ms，帧循环已无 delay 余量）。
3. **REQ-103 的「连续演奏」实际做成了「连续运行」**：11.2 分钟里学生玩了若干局并停留在主界面，不是从头到尾一直在演奏；未做自动演奏脚本。
4. P1（REQ-008/REQ-009）未开始，依赖 TF 卡与喇叭。
5. TC-007 的注入 FAIL 是编译期开关造出来的，不是运行时检测真实坏数据；真实坏数据（比如 TF 卡上的谱面）属于 P1 范畴。

后续建议：

1. **M3 第 4 步已完成**（`selftest.c`）。剩下的是收口：修正 L-11 的统计口径，再把 M3 的里程碑提交做实。
2. **L-08（HUD 底板遮挡 lane 0）需学生主观判定**：按几何推算 lane 0 预读比其他轨短约 280ms，但**未拍到实测画面**。如果玩起来觉得 lane 0 「突然冒出来」，可缩窄底板或换成两行 HUD。
3. REQ-104 若学生认可「点击→状态切换 + 已知 flush 迟到上限」这个拆解，可视为达标或改判据；否则需 GPIO 打点复测。
4. 音画同步（L-03）与 TF 卡到货绑定，采购优先（R-04）。
5. 三段视频（M2 启动、M3 两段）的网盘链接待学生补（L-07 / L-10）。
