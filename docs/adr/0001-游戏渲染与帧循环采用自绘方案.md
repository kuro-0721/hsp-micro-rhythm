# ADR-0001: 游戏渲染与帧循环采用自绘方案（不使用 LVGL）

- 状态：已采纳
- 日期：2026-10-10
- 决策人：kuro-0721　协助：GitHub Copilot（DeepSeek V4.1 Flash）
- 关联需求：REQ-002（音符下落渲染）、REQ-003（触摸判定）、REQ-101（帧率）、REQ-104（端到端延迟）

## 背景

音游的核心不是界面好不好看，而是「点击时刻」与「音符应命中时刻」之间的误差能不能被准确测量和稳定复现。
判定窗口计划为 Perfect ±60ms / Good ±120ms，这就要求：

- 帧节拍必须稳定，不能出现几十毫秒级的抖动，否则音符在屏幕上的位置与谱面时间对不上；
- 触摸事件的时间戳必须可靠，判定延迟必须可测量（REQ-104 要求给出数字）；
- 屏幕驱动 CO5300 支持 **TE/VSYNC 信号**（`customer/boards/Kconfig_lcd` 中 `LCD_CO5300_VSYNC_ENABLE` 默认 y），可以把刷帧对齐到屏刷新。

硬件约束：屏幕 390×450，QSPI 接口；PSRAM 8MB（OPI 144MHz），单帧 390×450×2B = 351KB，双缓冲 702KB，内存充裕。

## 备选方案

| 方案 | 优点 | 缺点 | 对需求/风险的影响 |
|---|---|---|---|
| A. 全 LVGL v8 实现 | 控件现成、开发最快、菜单/动画不用自己写 | SDK 的 `example/lvgl_v8_ttf` README 明确标注**「未验证」**；LVGL 的动画/定时器不保证帧间隔，判定时刻难以精确对齐；触摸到反馈的链路被 LVGL 屏蔽，REQ-104 不易测量 | REQ-002/101/104 的验收会变得困难甚至无法给出可信数字 |
| B. 自绘 framebuffer + 固定帧循环（参考 `example/lcd_fb`） | 帧间隔、判定延迟都是自己算的，可以直接打日志取数；可对齐 TE 信号防撕裂；不引入第三方 UI 依赖 | 所有绘制（音符、判定线、文字、结算页）都要自己写，工作量大 | REQ-002/101/104 都能给出可复核的数字；代价是开发时间 |
| C. 混合：LVGL 做菜单/结算，游戏场景自绘 | 界面开发省力，游戏层时序可控 | 两套渲染要共享帧缓冲/双缓冲，切换时的内存与时序协调复杂，且仍引入「未验证」的 LVGL | 权衡不错，但复杂度对单人课程项目偏高 |

## 决策

选择 **方案 B：自绘 framebuffer + 固定帧循环**。

理由：这个项目要证明的是「在 MCU 级硬件上做到手感跟得上节奏」，那么**时序指标本身就是交付物**。方案 B 把帧间隔和判定延迟握在自己手里，可以直接输出帧间隔统计与判定延迟直方图（REQ-007 的板上自检），这是最有说服力的证据链。方案 A 开发快，但恰恰把要证明的东西交给了不可控的第三方组件，而且它在本板还是「未验证」状态。方案 C 的复杂度对当前人力不划算。

## 后果

- 正面：帧率、判定延迟可测量、可打印；可对齐 TE 信号减少撕裂；无第三方 UI 依赖，构建风险低。
- 负面/代价：绘制代码全部自己写（音符、判定线、分数文字、结算页），开发工作量显著增加；字体渲染需要自己处理（可先用简单点阵字库）。
- 需要同步修改：`docs/02` 设计（渲染模块、帧循环、TE 对齐）、`docs/03` 测试计划（帧间隔与延迟测量方法）、`manifest.yaml` 的 `design.key_decisions`。
