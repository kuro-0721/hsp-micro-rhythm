# ADR-0004: 产品范围定为技术验证原型（不做面向玩家的成品）

- 状态：已采纳
- 日期：2026-10-10
- 决策人：kuro-0721　协助：GitHub Copilot（DeepSeek V4.1 Flash）
- 关联需求：`docs/01` §2 产品概述、§8 验收标准；REQ-001~REQ-009 的验收口径

## 背景

`docs/01` v0.1 的 §2 由 agent 起草，写成"一块能装进口袋的简易音游"、"目标用户是懂音游基本玩法、愿意在硬件上试玩的人"，**隐含了"面向玩家的成品"这一前提**，而它从未被明确决策过（原 §2 一直标注"待学生改写为本人判断"）。

学生（项目负责人）对此提出自己的判断：

1. 开发板受尺寸与交互条件限制，**不会有真人玩家长期在板上玩音游**，所以不能用"消费者级可玩性"来定验收口径；
2. 但这不代表项目没意义——现有音游大多跑在手机、电脑和**笨重的街机**上，**缺少为音游特化过的便携设备**；
3. 因此项目定位应是"技术验证原型"，**为以后可能出现的音游专用设备提供可行性参考**。

## 备选方案

| 方案 | 内容 | 优点 | 缺点 / 代价 | 对需求与进度的影响 |
|---|---|---|---|---|
| **A. 技术验证原型** | 只做到"能完整演示一局 + 帧率 / 判定延迟可测量"，不打磨曲库、UI、手感 | 时间可控；答辩聚焦一个可证伪的问题：MCU 级硬件到底能不能做到 | 演示观感朴素，可能被问"这算产品吗" | 与现有 P0 范围（REQ-001~007）一致；§8 验收口径需改为"可完整演示 + 数据可测量" |
| B. 面向玩家的口袋音游成品 | 多曲目 + UI 打磨 + 手感调校 + 续航 | 更接近"真产品"，产品感强 | 时间不够（M5 截止 11-15）；开发板无外壳、按键少，做不成真成品 | 需扩范围（曲库管理、UI 系统、成品化测试），M3~M5 有延期风险 |
| C. A + P1 音频 / 振动补"手感"证据 | P0 为验证原型，P1 用音频 + 振动提供节奏对齐与触觉反馈的证据 | 让"未来设备参考"多出"手感"这一维度 | 需额外采购并焊接马达（R-04 当前未到货） | 保留 P1（REQ-008/009），但仍是"验证"性质而非"打磨" |

## 决策

采纳 **方案 A：产品范围定为技术验证原型，不做面向玩家的成品**。由学生（项目负责人）拍板。

理由（学生原话）："开发板受限于大小，肯定不会有真人玩家去在上面玩音游，但就不代表它没意义了，现在的音游大部分在手机、电脑和笨重的街机，没有专门特化的音游玩具，我们这个项目可以为以后可能出现的音游专用设备提供参考。"

对应到文档的改动：`docs/01` §2.1 / 2.2 / 2.3 已按此改写（提交 `9ad35e4`）；§8 新增验收口径一条——以"作者 / 评审者能完整演示一局 + 数据可测量"为准，**不以消费者级可玩性为准**。

## 后果

- 正面：范围边界清晰，M3~M5 的时间压力可控；答辩叙事清晰（"我们回答的是可行性问题，不是做一个成品"）；与 ADR-0001（时序指标本身就是交付物）自洽。
- 负面 / 代价：演示观感朴素，说服评审要靠**数据**而不是**画面**；"产品感 / 创新性"这一评分维度需依靠"为未来音游专用设备探路"这一叙事来支撑，因此**帧率与判定延迟的实测数据必须扎实、可复现**。
- **未决事项（已于 2026-10-10 关闭）**：P1 **保留**（按方案 C 的性质执行：补证据，不做打磨）；但 REQ-009 的反馈形态由“震动”改为“特殊音效”——该子决策见 **ADR-0005**，并已在 `docs/01` §9 需求变更记录登记（CR-03）。
- 需要同步修改：`docs/01`（§2、§8）、`docs/02`（§7 决策表）、`docs/00`（§1 概述、§4 里程碑表——此处 agent 当时漏改，2026-10-10 补）、`manifest.yaml`（`design.key_decisions`）。

## AI协作

学生主动提出定位判断（"不会有真人玩家长期玩" + "缺少为音游特化的便携设备"），agent 将其归纳为三个备选并列出代价对比，学生拍板选 A。**agent 原稿 §2 隐含的"成品"定位被学生明确否决**，该稿件已随提交 `9ad35e4` 废弃，仍可在 git 历史中查看。
