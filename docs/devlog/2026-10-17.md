## 遇到的问题与解决

1. **抓取脚本的时序设计错了**。现象：第一次抓取只拿到 2 行就报 `对端口"COM9"的访问被拒绝`（`UnauthorizedAccessException`）。根因：脚本先打开 COM9、学生后拔插，USB 重新枚举使旧句柄失效。解决：脚本改为**容错重连**（捕异常→关端口→重试 Open），重抓成功（116 行）。教训：涉及 USB 拔插的抓取，脚本必须能忍受端口消失/重现，不能假设一次 Open 管到底。
2. **check_all 未通过却照常提交**。现象：提交 `d047ba5` 时 `check_all.py` 已报「开发日志 FAIL」（当日日志是空模板），我没有做条件判断就直接 commit 了。解决：随后补填本日志。教训：check 与 commit 之间要有条件判断，不能无条件用 `;` 串联。
3. **帧率回归：p95 从 33ms 变 34ms，没查清根因**。第 2 步引入触摸后，6 档密度的 p95 全变成 34ms（flush 27~30ms）。排查过程：
   - 假设一「bridge 线程优先级抢占帧循环」→ 把 bridge 从 19 改成 25（降到帧循环 game=20 之后）实测 p95 **仍是 34ms**，假设被证伪。
   - 假设二「触摸事件突发拖慢」→ 让学生全程不碰屏幕重测，真实触摸事件 **0 条**，p95 **仍是 34ms**，也被证伪。
   - 假设三「触摸驱动自己在 120Hz 持续采样」→ 读 SDK 源码 `drv_touch.c` 确认 `BSP_TOUCH_SAMPLE_HZ` 默认 120（本项目 `rtconfig.h` 未覆盖），即约每 8.3ms 主动读一次 I2C。**但这一点没有做实验验证，只是代码阅读得出的假设**，不能当结论。
   - 另一层不确定性：打点用 `rt_tick_get_millisecond()`，分辨率只有 1ms，34 与 33 正好卡在边界上，**分不清是 33.x 还是真的 34.x**。
   - 结果：agent 给出三个方案（A 用 DWT 周期计数器做亚毫秒测量 / B 直接放宽判据 / C 停下优化这 1ms）并推荐 A；**学生选择 B**，按 CR-04 把判据改为 ≤34ms。agent 已把「未测准」写进 R-10 与 `known_issues`，没有把 34ms 说成「已验证达标」。
4. **`export.ps1` 报 uv 缺失，终端无法编译**。现象：`uv was not found in PATH`，`where uv` 全空，扩展目录里也搜不到 uv.exe。解决：改用 CodeKit 的编译通道（`scons --board=sf32lb52-lchspi-ulp -j8`）编译成功，`exitCode 0`。这条与 P-02 / CR-02 仍待处理直接相关——**uv 现在不是「没加 PATH」，而是本机根本没有**，上次会话「临时加 PATH」的做法已经不可复现。
5. **提交信息被钩子误判为「还有未替换的占位符」**。现象：正文里写 `P95 <= 33ms` 和 `33ms -> 34ms`，`check_commit_msg.py` 的 `PLACEHOLDER_RE = <[^>]*>` 把这两个符号连成了一个假的尖括号占位符。解决：改写为「不超过 34ms」并去掉箭头，重新提交通过。教训：提交正文里避免出现裸的 `<` / `>`。
6. **agent 占用串口导致学生烧录失败**（已登记为 P-10）。现象：学生反馈「烧录失败了」，同时 agent 的 180 秒抓取正开着，`scene_run2` 日志里只有旧固件的 `[LOOP]` 行（frames 7500~9900）。根因：抓取与 CodeKit 烧录争用同一个 COM9，而 agent 先占用了它。解决：杀抓取进程 → 确认 COM9 可独占打开 → 删掉误产生的无效日志 → 改为「先烧录、再抓串口、最后复位」。教训：串口是独占资源，安排步骤时必须考虑谁先占。
7. **抓取脚本首次打开失败就整体退出**。现象：第一次启动抓取时报 `端口 COM9 不存在`，脚本直接抛异常结束。根因：脚本把初始 `$sp.Open()` 放在重试循环之前，重连逻辑只能处理后续拔插，管不了第一次就碰不到端口的情况。解决：删掉循环前的 `Open()`，让循环内的 `if (-not $sp.IsOpen)` 负责首次打开并享受同一套 try/catch 重试，之后顺利抓到完整启动日志（含 ROM 引导阶段）。
