# M5 答辩：实现方式详解与提问应答

> 这份文档解决的是「**老师问"你是怎么做的"时，你能不能讲到代码级**」。
> 所有函数名、常量、数值都能在 `src/` 里对上；出处标在每节末尾。
> 配合 `docs/guides/M5-答辩准备指南.md`（时间分配、幻灯片大纲、答辩策略）一起用。

## 0. 整体架构

### 0.0 先给结论（30 秒版本）

> 「SDK 负责所有硬件时序，我在它上面写了 **3 层自研模块**（平台适配 → 业务逻辑 → 调度），
> 用**一个帧线程**把所有逻辑和绘制串成固定 33ms 的节拍，**两个中断只做两件最轻的事**
> （触摸打时间戳、音频 DMA 计数），音频混音完全交给 SDK 音频服务端。谱面时间轴不自己计时，
> 而是直接读音频播放进度。」

### 0.1 分四层看（谁写什么，边界在哪）

| 层 | 模块 | 职责 | 谁写的 |
|---|---|---|---|
| ① 驱动层 | SDK 的 `lcd` / `touch` / `audio_server` / `mp3ctrl` / PSRAM HAL | 总线时序、DMA、编解码、显示窗口、VSYNC 回调 | SDK v2.5.1，我只调 API |
| ② 平台适配层 | `fb.c` `gfx.c` `input_touch.c` `audio.c` `sfx.c` | 把 SDK 的异步/回调/资源模型包成项目要的语义（例如「提交一帧并等完成」「触摸事件带中断时刻」） | 自研 |
| ③ 业务逻辑层 | `scene.c` `judge.c` `chart.c` | 状态机、判定规则、计分、谱面解析——**纯逻辑，不碰硬件** | 自研 |
| ④ 调度层 | `game_loop.c` | 固定 33ms 帧循环、帧统计、初始化顺序 | 自研 |
| 横切 | `selftest.c`（自检）、`autoplay.c`（压测注入，交付版关闭） | 不参与主流程，只被调用 | 自研 |

**边界的意义**：③ 层不 `#include` 任何驱动头文件，所以判定逻辑可以脱离硬件做批量测试
（`judge_bulk_test()` 就是这么跑的）；① 层的东西一处都不用改，换屏幕只要动 `fb.c`。

### 0.2 模块清单：谁管什么、手里攥着什么数据

| 文件 | 职责 | 持有的关键数据 | 依赖 |
|---|---|---|---|
| `game_loop.c` | 帧循环 + 帧间隔统计 + 启动顺序 | 环形缓冲 `s_st`（`RING_LEN 256`） | 全部 |
| `fb.c` | 整屏帧缓冲与提交 | `s_buf`（351,000B @PSRAM）、`s_flush_sema` | SDK `lcd` |
| `gfx.c` | 5×7 点阵字与矩形/线 | `s_font5x7[59][5]` | 帧缓冲 |
| `scene.c` | 三态状态机 + 三页渲染 | `s_scene`、`s_chart_ms`、`s_chart_use_audio` | judge / chart / gfx / sfx |
| `judge.c` | 三档判定 + 计分 + 延迟直方图 | `s_notes[256]`（谱面副本）、`s_stat` | 无（纯逻辑） |
| `chart.c` | 文本谱面解析 | `s_notes`（解析结果）、`s_info`（摘要） | 调用 `judge_load()` 交付 |
| `audio.c` | MP3 播放 + 音频时间基准 | `s_mp3` 句柄、`s_dma_ticks` | SDK `audio_server` / `mp3ctrl` |
| `sfx.c` | 合成音效 + 常驻喂 PCM | `s_pcm[2205]`、`s_client`、`s_play_pos` | SDK `audio_server` |
| `input_touch.c` | 中断打戳 + 读点 + 事件队列 | `s_queue[32]`、`s_pressed` | SDK `touch` |
| `selftest.c` | 三节自检与总结论 | 无长期状态 | judge / chart / loop_stats |

> 关键点：**谱面有两份副本**——`chart.c` 解析出来的，和 `judge.c` 自己 `memcpy` 的那份。
> 判定只动 judge 的副本（`state` 字段），所以重开一局只需 `judge_reset()`，不必重新解析谱面。

### 0.3 并发模型：2 个中断 + 5 个线程

```
优先级          名称            栈      干什么
(高)
  ──  触摸 rx_indicate(中断)      —      只打时间戳 + release 信号量
  ──  音频 TX DMA 回调(中断)      —      只把 s_dma_ticks++（s_playing 为假时不计数）
  18  tp    触摸读点线程        2048    等信号量 → I2C 读点 → pressed 去抖 → 入队
  20  game  帧循环              8192    每 33ms：update → render → present → 补节拍
  22  aplay MP3 起播（一次性）   2048    调 mp3ctrl_play()（内部阻塞等开播），返回即退出
  22  audio_test 上电自测       4096    交付版空转（AUDIO_BOOT_TEST=0）
  24  sfx   音效喂数据          2048    回调驱动：有音效填音效样本，否则填静音
  26  autoplay 测试注入点击     2048    交付版不创建（AUTOPLAY_ENABLE=0）
(低)
```

**优先级为什么这么排**：触摸要最快响应（18）→ 帧循环是主时间线（20）→ 起播可以等（22）→
**音效必须低于帧循环（24）**，否则混音会挤占帧预算（这是 R-09 的结论）→ 自动演奏最低（26），
不能干扰正在测的东西。

**两个中断里都只做一件事**：触摸中断打时间戳（判定精度不能被 I2C 读点污染），
音频中断只累加计数（换算放 `audio_pos_ms()` 里做，中断里不做除法）。

### 0.4 三条数据流

**① 输入流**（每次点击一次，不等帧）

```
FT6146 ──中断──▶ rx_indicate: s_isr_ms = now; release(sema)
                          ▼
        tp 线程: rt_device_read() → 只认 DOWN → pressed 去抖 → tp_push(isr_ms,x,y)
                          ▼
        s_queue[32]（单/双生产者，game 线程每帧清空）
                          ▼
        game 线程: lane = x / (w/4)；chart_ev = chart_ms − (now − ev.t_ms)
                          ▼
        judge_touch(lane, chart_ev) → 计分/Combo/Acc + judge_latency_add(lag)
                          ▼
        命中则 sfx_trigger()（返回发声时刻，日志打 delta = trigger − judge）
```

**② 渲染流**（每帧一次）

```
game 线程: scene_render() ──▶ 直接写 PSRAM 帧缓冲 s_buf（351,000B）
                              fb_clear → 轨道线 → 可见音符 → HUD 底板 → 文字
                          ▼
        fb_present(): mpu_dcache_clean(351,000B)
                      set_window(0,0,389,449)
                      draw_rect_async(全屏)
                      rt_sem_take(s_flush_sema)  ◀── LCD tx_complete 回调 release
                          ▼
                      LCD 面板
```

**③ 音频流**（BGM 与音效在服务端混合，各是一个 client）

```
aplay 线程 ─ mp3ctrl_open_buffer(内嵌 mp3 数组) ─ mp3ctrl_play()（阻塞等开播）
                                                        │
sfx 线程 ─ 回调里 audio_write(441 样本/次，无音效写静音) ─┤
                                                        ▼
                                     SDK audio_server：软件混音 (a>>1)+(b>>1)
                                                        ▼
                                              DAC → 功放 → 喇叭
                                                        │
                                     TX DMA 回调：s_dma_ticks++ ──▶ audio_pos_ms()
                                                        ▼
                              game 线程: chart_ms = audio_pos_ms()（谱面时间轴）
```

**时间基准的方向是反的**：不是「游戏时间推着音频走」，而是「音频播到哪，谱面就到哪」。
这样即使 BGM 起播晚了几百毫秒，音符和声音也天然对齐。

### 0.5 一帧内的时间预算（实测数字，讲 REQ-101 时用这张）

```
 帧起点 t0 ──────── t1 ────────────────────────────── t2 ───────── 下一帧
 │ scene_update │        scene_render (draw)        │fb_present(flush)│delay
 │    < 1 ms    │          10 ~ 11 ms               │    21 ~ 22 ms    │ ~0 ms
 └──────────────┴───────────────────────────────────┴──────────────────┘
                        合计 work ≈ 33 ms  /  预算 33.3 ms（30fps）
```

- `draw` 的 10~11ms 主要是**PSRAM 里整屏擦 351KB**（帧缓冲在 SRAM 时这一项只有 2ms）；
- `flush` 的 21~22ms 里，约 15.8ms 是**等一个 VSYNC**，剩下的才是传输；
- 所以「想提帧率」不能靠优化绘制，必须先解决「每帧擦 351KB」这件事——这正是 B3 脏区方案想解决、
  但因拖影被回退的那条路。

### 0.6 数据所有权与同步方式（被问「有没有竞争」时用）

| 数据 | 谁写 | 谁读 | 同步方式 |
|---|---|---|---|
| 场景状态 / 判定统计 / 谱面 | 只在 `game` 线程 | 同左 | **不需要锁**（单线程状态机） |
| 触摸队列 `s_queue` | `tp` 线程 + `autoplay` 注入 | `game` 线程 | `rt_enter_critical()` 保护 head/tail |
| 帧统计 `s_st` | `game` 线程 | 自检、结算页 | `rt_mutex` |
| `s_dma_ticks` | 音频中断 | `game` 线程 | `volatile`（32 位读写原子） |
| `s_play_pos` / `s_playing` | 音频回调线程 | 判定线程 | `volatile` |
| 帧缓冲 `s_buf` | `game` 线程 | LCD 的 DMA | `mpu_dcache_clean()` 保证可见性 |

**一句话**：「业务状态全在一个线程里，所以没有锁；只有跨线程的队列、统计计数和音频计数需要保护，
分别用临界区、互斥量和 `volatile`。」这句话能挡掉大部分并发追问。

### 0.7 被追问架构时怎么答

| 追问 | 答法 |
|---|---|
| 为什么不用定时器/事件驱动，而是固定帧循环？ | 音游必须有稳定的画面节拍，固定帧循环让「渲染时刻可控」；逻辑也挂在同一节拍上，时间关系简单可验证。事件驱动反而要处理「一帧内多次事件」的合并问题 |
| 为什么不用现成 GUI 框架（LVGL 等）？ | 需求只有 3 个页面 + 点阵文字 + 矩形，引入框架的 RAM 与刷新策略不可控，且会掩盖帧预算问题。自绘 224 行的 `gfx.c` 就够 |
| 模块之间为什么用函数调用不用消息队列？ | 除触摸外都是同线程调用；触摸之所以用队列，是因为中断/线程与帧循环不同步，需要把「事件发生时刻」一起带过来 |
| 一个帧线程够吗？音频为什么不放帧循环里？ | `mp3ctrl_play()` 会阻塞到真正开播，放帧循环里会卡住整帧，所以单独起 `aplay` 线程；音效走回调驱动，独立线程 |
| 层级划分有什么实际好处？ | 判定逻辑不依赖硬件，所以能跑 50 次批量测试和边界值自检；帧缓冲换位置（SRAM→PSRAM）只动 `fb.c` 一个文件 |

## 1. 上电到出分：代码执行顺序

`app_start()`（`src/game_loop.c` 末尾）严格按下面顺序初始化，**顺序本身是有原因的**：

| 步骤 | 调用 | 为什么必须在这个位置 |
|---|---|---|
| 1 | `fb_init()` | 后面所有绘制都依赖帧缓冲；先试 PSRAM、失败回退堆 |
| 2 | `judge_init()` | 判定引擎要先把音符池清零 |
| 3 | `selftest_startup()` | 先跑判定/谱面自检，**必须在加载好谱面之前测错误谱面**，否则会把好谱面冲掉 |
| 4 | `touch_init()` | 场景状态机需要触摸事件 |
| 5 | `scene_init()` | 进入 TITLE |
| 6 | `audio_start_async()` | 只注册 DMA 回调并设音量，不阻塞 |
| 7 | `sfx_init()` | 首个 audio client 由它打开，**它决定设备采样率** |
| 8 | `autoplay_start()` | 仅测试用，交付版 `AUTOPLAY_ENABLE 0` |
| 9 | `game_loop_start()` | 最后启动帧循环 |

**帧循环每帧做四件事**（`game_thread()`）：

1. `scene_update(t0)` —— 出队全部触摸事件、推进判定、检查状态切换
2. `scene_render()` —— 只写背缓冲，不提交
3. `fb_present()` —— `mpu_dcache_clean` → `set_window` → `draw_rect_async` → 等信号量
4. 补满节拍 —— 本帧耗时不足 33ms 就 `rt_thread_delay` 补齐

→ 出处：`src/game_loop.c`（`FRAME_MS 33`、`game_thread()`、`app_start()`）

## 2. 逐功能：怎么做的

### 2.1 REQ-001 主界面与状态机

**怎么做**：`scene.c` 用一个 `enum scene_id`（TITLE / PLAYING / RESULT）加三个 `enter_xxx()` 函数。
所有状态读写都只发生在帧循环线程里，所以**整个 scene.c 没有一个互斥量**——单线程状态机不需要锁。

进入 PLAYING 时同时记两个时间戳：`now_ms`（帧开始）和 `tap_ms`（触摸中断时刻），
两者相减就是「点击→状态切换」延迟，实测 14/17ms。**必须记 tap_ms**，否则 TC-001 的「点击后 1s 内进入演奏」
在日志上无法验证（只能看到"什么时候切的"，不知道"什么时候点的"）。

RESULT 页 30 秒无操作自动回 TITLE（`RESULT_TIMEOUT_MS 30000`）。

**一句话讲法**：「三态状态机，纯单线程无锁，状态切换时把触发它的触摸时刻一起记进日志，这样延迟可验证。」

→ 出处：`src/scene.c`（`enter_title/enter_playing/enter_result`、`scene_update()`）

### 2.2 REQ-002 音符下落与渲染

**怎么做**：音符位置**只由时间差算出来，不存坐标**：

```
y = judge_y - (note.hit_ms - chart_ms) * NOTE_SPEED_PX_S / 1000
```

`NOTE_SPEED_PX_S = 300`，`judge_y = height - 70`。所以 `chart_ms == hit_ms` 那一刻音符正好压在判定线上。
过线超过 `NOTE_FADE_MS (200ms)` 不再绘制；还在屏幕上方（`dt` 超过屏幕高度换算值）直接跳过——
这两个判断就是**可视裁剪**，省掉大部分无效绘制。

每帧 `fb_clear(COL_BG)` 全屏擦一次，再画 4 条轨道分隔线、双像素判定线、可见音符、HUD 底板与文字。

**一句话讲法**：「音符不存坐标，每帧用 `(hit_ms − chart_ms) × 落速` 算 Y，所以画面和时间轴天然严格对应。」

→ 出处：`src/scene.c`（`render_playing()`）

### 2.3 REQ-003 三档判定

**怎么做**：`judge_touch(lane, t)` 在该轨上扫一遍所有 `state == 0`（未判定）的音符，取 `|t − hit_ms|` 最小的那个：

- `≤ 60ms` → PERFECT（`JUDGE_PERFECT_MS`），加 100 分
- `≤ 120ms` → GOOD（`JUDGE_GOOD_MS`），加 50 分
- **`> 120ms` → 返回 `JUDGE_NONE`，既不消耗音符也不判 MISS** ← 这条最容易被忽略

第三条是为了「讲道理」：否则玩家提前乱点，会把后面的音符白白吃掉。
命中后 `state = 1`，一次点击最多消耗一个音符（REQ 明确要求）。

MISS 不在 `judge_touch` 里产生，而在每帧的 `judge_tick(chart_ms)` 里：`now > hit_ms + 120` 且未判定 → MISS、Combo 归零。

**关键细节：判定用的是「触摸发生那一刻」的谱面时间**。触摸事件要等下一帧才被取出，最多滞后一帧（33ms），
而 TC-008 的判据才 50ms，这 33ms 不能不算。所以 `scene_update()` 里做补偿：

```
chart_ev = chart_ms - lag     // lag = now_ms - ev.t_ms
```

**一句话讲法**：「找最近的未判音符，60/120ms 两档；超窗不消耗；MISS 由 tick 按时推进产生；
判定用的是事件时刻而不是帧时刻，补偿了一帧量化误差。」

→ 出处：`src/judge.c`（`judge_touch()`、`judge_tick()`）、`src/scene.c`（`lag` / `chart_ev` 计算）

### 2.4 REQ-004 分数 / Combo / Acc

**怎么做**：PERFECT +100、GOOD +50（P0 不设 Combo 倍数，避免规则复杂化）。
Combo 命中 +1、MISS 归零，`max_combo` 单独记。

Acc 用整数定点，存成「百分比 ×100」：

```
acc_x100 = (perfect × 10000 + good × 5000) / judged
```

MISS 计入分母、得分为 0。用 `uint64_t` 中间量防止 `judged` 很大时溢出。

**一句话讲法**：「加权命中率，PERFECT 记满、GOOD 记一半，整数定点保存两位小数，避免浮点。」

→ 出处：`src/judge.c`（`recalc_acc()`、`SCORE_PERFECT/GOOD`）

### 2.5 REQ-005 结算与重开

**怎么做**：`judged >= chart_note_count()` 就 `enter_result()`——**用「已判数量」而不是「时间到」触发**，
这样即使漏点也能正常收尾。结算打印四项数据（score / max_combo / acc / P·G·M）供 TC-005 对比。

重开不重新解析谱面，只 `judge_reset()` 把 `state` 与统计清零（谱面在启动时解析一次，存在 `s_notes` 里）。
重开时还必须重置音频时间基准相关变量（`s_chart_audio_gone`、`s_chart_fallback_*`），否则第二局会沿用上一局的 fallback 状态。

**一句话讲法**：「按已判音符数切结算，不是等定时器；重开只清状态不重解析谱面。」

→ 出处：`src/scene.c`（`enter_result()`、`enter_playing()`）

### 2.6 REQ-006 文本谱面解析

**怎么做**：手写解析器（不引 libc 的 `sscanf`，避免浮点/格式开销）。格式每行 `<时间戳ms> <轨号0-3>`，`#` 到行尾是注释。

校验五条：时间戳 ≤ 3600000、轨号 ≤ 3、两字段之间必须有空白、轨号后只能是空白或注释、
**时间戳必须单调不减**（乱序会让 `judge_touch` 的「最近音符」选错对象，必须在加载时暴露）。
失败返回 `-(行号)`（行号从 1 起），与 TC-006 的判据一致。

内置谱面 58 个音符、120BPM（间隔 500ms）、首 1000ms、末 29500ms，4 轨轮转，
且**同轨相邻音符间隔 ≥2000ms**，不可能踩到 ±120ms 窗口。

**一句话讲法**：「文本格式 + 五条语法校验 + 失败返回负行号；特意校验单调性，因为乱序会让判定选错音符。」

→ 出处：`src/chart.c`（`chart_parse()`、`s_builtin_chart`）

### 2.7 REQ-007 启动三节板上自检

**怎么做**：开机在 `selftest_startup()` 里跑，分三节，任一节失败总结论即 FAIL：

| 节 | 内容 | 实现位置 |
|---|---|---|
| 1/3 谱面 | 先喂一份**故意错误**的谱面（第 2 行轨号 9），期望返回 `-2`；再加载内置谱面，校验「58 个音符 / 末音符 29500ms」 | `section_chart()` |
| 2/3 判定 | 8 个窗口边界值（±60 / ±61 / ±120 / ±121）、一次点击只消耗一个音符、Combo 与归零、Acc=75.00% 与 score=150、跨轨不互扰；再跑 50 次已知偏移的批量判定 | `judge_selftest()` + `judge_bulk_test(50)` |
| 3/3 帧率 | **必须等跑够 `SELFTEST_FRAME_WINDOW` 帧**才输出（否则样本不足 p95 无意义），判据 `p95_interval ≤ 34ms` | `selftest_frame_stats()` |

还有一个编译期开关 `SELFTEST_INJECT_BAD_CHART`，置 1 时第 1 节与总结论都会 FAIL，
用来证明「自检真的会失败」，而不是永远打印 PASS。

**一句话讲法**：「自检分三节、失败可传染到总结论；判定用边界值而不是随便敲；还留了注入开关证明自检会 FAIL。」

→ 出处：`src/selftest.c`、`src/judge.c`（`judge_selftest()`）

### 2.8 REQ-008 播放 MP3 + 音频时间基准

**怎么做**（三件事）：

1. **曲目在固件里**：`mp3_sample.c` 是 MP3 字节数组，`mp3ctrl_open_buffer()` 直接从 flash 解码，不挂文件系统。
2. **必须异步起播**：`mp3ctrl_play()` 内部是 `rt_event_recv(RT_WAITING_FOREVER)`，会阻塞到真正开播。
   在帧循环里同步调会把画面卡住，所以 `audio_play_async()` 起一个短命线程（`aplay`，prio 22，2048 栈）去播。
3. **时间基准取「真正被 DAC 取走」的样本数**：注册 `audio_register_10ms_tx_dma_callback()`，每次回调累加计数，
   再换算 `pos_ms = ticks × 每 DMA 样本数 × 1000 / 采样率`。

第 3 点的坑我踩过：回调名字里有 "10ms"，但**实际周期 = 一次 DMA 的样本数 ÷ 采样率**。
开混音时 `TX_DMA_SIZE = 320` 字节 = 160 样本，160/44100 ≈ **3.63ms**，按 10ms 累加会放大 10/3.63 ≈ 2.756 倍，
表现为 8.05 秒的曲子报 22180ms。所以 `AUDIO_DMA_SAMPLES` 跟着 `SOFTWARE_TX_MIX_ENABLE` 取值，不写死。

还有两个工程处理：
- 进 PLAYING 后若 `pos == 0` 且还没到 `CHART_AUDIO_GRACE_MS (1500ms)`，判定为「BGM 线程还没起来」，不误判；
- 测试曲只有 8.05s，而谱面到 29.5s。音频播完后 `pos` 会停在 8050，谱面就不动了 →
  检测到音频结束就从那一刻起改用 tick 续算，并在日志里 `WARN` 明确告知。

**一句话讲法**：「进度不用解码器查（没有 ms 级接口），而是数 TX DMA 回调 × 每回调样本数 ÷ 采样率；
回调名叫 10ms 但实际是 3.63ms，这一点我特意写进了代码注释和报告。」

→ 出处：`src/audio.c`（`audio_pos_ms()`、`audio_play_async()`）、`src/scene.c`（`chart_time_compute()`）

### 2.9 REQ-009 命中音效

**怎么做**：

- **波形是代码合成的**，不加载音频文件：440Hz 方波 → 一阶低通 `y += (x−y)/4` 软化 → 指数衰减包络
  （`env -= env>>7`，半衰约 5.5ms），50ms 时长，全整数运算不依赖 libm。
- **播放走回调驱动**：audio client 在写缓存半空/空时回调要数据，应用在回调里 `audio_write` 补齐；
  **没有音效时也要一直喂静音**，因为音频链路一旦断流不会自己恢复，不断流才能在触发瞬间立刻出声。
- **延迟控制**：延迟 ≈ 等下一次「缓存半空」回调的时间。cache 取 4096 字节、块 **441 样本（10ms @44.1kHz）**，
  与回调周期 1:1，既不堆积也不欠载；若用常见的 2048 字节缓存，最坏等 32ms 必然超过 20ms 判据。
- **音量不能取 15**：`audio_server.c` 里有一段只在 `vol == AUDIO_MAX_VOLUME` 才执行的特殊增益分支，
  取 15 会踩进去，实测表现是「每敲一次更响一次」；取 14 绕开。
- **采样率取 44100 不取 48000**：混音目标采样率由**第一个打开的 client** 决定，sfx 先开；
  若 sfx 用 48k，MP3(44.1k) 每 10ms 都要重采样一次，实测帧间隔 p95 从 34ms 恶化到 36ms。统一 44.1k 走直通分支。
- **开关**：TITLE 页有一个 160×34 的按钮，矩形由 `title_sfx_btn()` 统一计算，渲染与命中判定共用同一份坐标，
  避免两处算错。点击切换 `sfx_set_enabled()`，日志打印 `[SFX] toggle ... enabled=0/1`。

**判据怎么来的**：`sfx_trigger()` 返回「决定发声」的时刻，日志里打印 `delta = trigger_at − judge_at`；
另外记录 `sfx_feed_latency_ms()`（首样本进音频缓存的延迟），这个更接近真实发声但**仍不含 DAC 与喇叭时延**——
这个局限我写在了 `sfx.c` 文件头和测试报告里，不冒充端到端延迟。

**一句话讲法**：「音效是代码合成的 440Hz 衰减音；回调驱动持续喂数据（没音效喂静音）保证触发即响；
缓存与块大小按 10ms 回调周期倒推，才压得进 20ms 判据。」

→ 出处：`src/sfx.c`（`synthesize()`、`SFX_BLOCK_SAMPLES 441`、`SFX_VOLUME 4`）

### 2.10 REQ-104 触摸输入链路

**怎么做**：中断里**只做两件事**——`rt_tick_get_millisecond()` 打时间戳、释放信号量。
读点（I2C）放在 `tp` 线程（prio 18）里做，M2 实测中断→读点 <1ms。这样判定的时间精度不会被 I2C 耗时污染。

驱动有个坑：手指在屏上拖动时会**持续报 DOWN**（间隔约 11ms、坐标渐变）。
若「DOWN 就入队」，一次拖动会被拆成几十次点击，直接污染判定。所以维护 `s_pressed` 状态：
DOWN 只在「尚未按下」时入队，UP 才清除；再加 1s 兜底防止 UP 丢失卡死。
P0 只做点击判定，MOVE 一律忽略。

队列是单生产者单消费者环形队列，消费者 `touch_pop_event()` 用 `rt_enter_critical()` 保护；
后来加了自动演奏的注入接口 `touch_inject()`，变成两个生产者，所以 `tp_push()` 也进了临界区。

**一句话讲法**：「中断只打时间戳，读点在线程里做；用 pressed 状态机把「拖动连续 DOWN」压成一次点击。」

→ 出处：`src/input_touch.c`

### 2.11 REQ-102 帧缓冲与内存

**怎么做**：390×450×2 = **351,000 字节**。系统堆只有 **435,468 字节**（`__bss_end` 0x20015724 → 0x2007fc20），
这一块就占 80%，直接导致第二个 audio client 分配不到 ring buffer（实测断言）。

所以帧缓冲优先放 PSRAM `0x60100000`（8MB 基址偏移 1MB，避开尾部 NMI 保留区），并且**带自检**：
首尾各写探子 0x5AA5/0xA55A、`__DSB()`、读回比对；不过就 `rt_malloc` 回退——宁可费堆也不黑屏。

刷屏前必须 `mpu_dcache_clean()`，因为 PSRAM 可缓存，DMA 直接读内存会读到旧数据。

还有一个约束值得讲：`fb_flush_rect()` 只支持**整宽条带**。因为 `set_window + draw_rect_async` 要求缓冲在内存里连续，
而只有整宽区域在整屏缓冲里才连续。其它形状会退回整屏提交并只警告一次——
避免出现「看起来只刷一块、实际刷了 N 次 VSYNC」这种把性能偷偷吃掉的隐性行为。

**一句话讲法**：「351KB 搬到 PSRAM 并做读写自检，失败自动回退堆；刷屏前清 cache；
脏区接口只允许整宽条带，否则退回整屏，防止隐性性能损失。」

→ 出处：`src/fb.c`

### 2.12 图形与字体（顺带，常被问）

**怎么做**：不引第三方字库，自带 **5×7 点阵字体**（`s_font5x7[59][5]`，覆盖 0x20~0x5A），
`gfx_text()` 按 `scale` 把每个点放大成 scale×scale 方块，`scale` 上限 4 防止误传把整屏写满。
`gfx_fill_rect()` / `gfx_hline()` / `gfx_vline()` 都直接写帧缓冲。
全部自己写，也因此天然满足 REQ-105「无第三方素材/字体」。

## 3. 老师可能追问的实现问题

### 3.1 大概率会问（务必背下来）

| 问题 | 答题要点 |
|---|---|
| **帧率是怎么测的？** | 环形缓冲 256 个样本，同时记两类量：`work`（draw+flush 处理耗时）和 `interval`（本帧开始 − 上帧开始）。p95 是 `qsort` 排序后取 `n×95/100`。首帧 interval 不计（那是"上电到首帧"，会污染 p95）。掉帧判据是 `interval > 33+5ms` |
| **为什么每帧全屏擦？不能用脏区吗？** | 试过脏区，`draw` 从 10ms 降到 1ms、drop 20→1，但画面出现音符拖影，被我否决回退。原因是我先让 agent 做了优化、只看了指标没先看画面——这条写进了风险台账 AI-11 |
| **33ms 一帧，判定精度够吗？** | 判定用的是**触摸中断时刻**换算的谱面时间，不是帧时刻，所以不受 33ms 帧率限制；帧率只影响"看到的画面"，不影响"判的时机" |
| **为什么单缓冲不用双缓冲？** | M2 实测瓶颈是每次提交等一个 VSYNC（≈15.8ms），不是带宽；分行刷 8 次提交 → 132ms/帧。整屏单提交就降到 29~31ms，双缓冲解决的是撕裂而不是这个瓶颈。撕裂当前没观察到（单缓冲 + 等 VSYNC 完成已同步） |
| **`judge_touch` 是 O(n) 扫描，58 个音符够吗？为什么不做二分？** | 58 个音符 × 每帧最多几次点击，线性扫描开销可忽略；而且 `state` 会变，二分要找"未判的最近音符"反而更麻烦。如果谱面上千音符再改成按时间有序指针推进 |
| **MISS 为什么不在点击里判？** | MISS 是"时间过了还没人点"，与点击无关。放在每帧 `judge_tick(chart_ms)` 里统一推进，逻辑单一、不会漏 |
| **谱面为什么要求单调不减？** | `judge_touch` 取"最近的未判音符"，乱序会让它选错对象。这种错误必须加载时暴露，不能留到演奏中 |
| **音频进度为什么不用解码器接口？** | `mp3ctrl` 没有 ms 级进度查询（只有 loop/换文件/优先级/淡出），回调只给「秒」，精度不够。数 TX DMA 回调反映的是**真正被 DAC 取走**的样本，比数解码样本更准（解码样本还含在缓存里没播的部分） |
| **为什么起播必须异步？** | `mp3ctrl_play()` 内部 `rt_event_recv(RT_WAITING_FOREVER)` 阻塞到真正开播才返回，在帧循环里同步调用会卡住整帧 |
| **音效为什么要一直喂静音？** | 音频链路一旦断流不会自己恢复，只有持续有数据 DAC 才保持运行，触发瞬间才能立刻出声。代价是链路常开（功耗与底噪），已记为已知限制 |
| **音量为什么取 4 不取 15 最大？** | `audio_server.c` 有一段只在 `vol == AUDIO_MAX_VOLUME` 才执行的额外增益分支，取 15 会踩进去，实测「每敲一次更响一次」；而且 BGM 与音效共用同一个音量槽，4 档（-28dB）是试听后定的 |

### 3.2 深挖型（答不上来可坦白）

| 问题 | 答题要点 |
|---|---|
| 触摸去抖为什么用 1s 兜底？ | UP 事件可能丢失（例如手指滑出屏区），1s 后允许重新识别为「新的一次按下」，防止状态卡死。严格说这是兜底而非常规去抖 |
| 队列满了怎么办？ | `tp_push` 丢弃**最新**事件并计数 `s_dropped`（不覆盖旧事件，保证时间顺序）。P0 每帧都清空队列，实际不会满 |
| 自检第 3 节为什么要等帧窗口？ | 开机瞬间样本不足，p95 无意义。所以固定跑到 `SELFTEST_FRAME_WINDOW` 帧才输出一次 |
| 帧统计为什么要加互斥量？ | `loop_stats()` 会被自检/结算页读，`stats_add()` 在帧线程写，跨线程读所以加锁 |
| 多线程优先级怎么排的？ | `tp(18) < game(20) < aplay(22) < sfx(24) < autoplay(26)`。触摸要最快响应；音效必须低于帧循环，否则混音会挤压帧预算（R-09） |
| `local` 音量槽是什么问题？ | BGM 与音效 audio_type 都是 `LOCAL_MUSIC`，`private_volume` 按类型存一份，后设置的生效 → 两个宏必须一起改（L-14） |
| 为什么音效采样率从 48k 改 44.1k？ | 混音目标采样率由第一个 client 决定；sfx 用 48k 会迫使 MP3 每 10ms 重采样，p95 从 34 → 36ms |

3. `audio.c` 的 `audio_pos_ms()` —— 能讲清"回调次数 × 每回调样本数 ÷ 采样率"，以及为什么不能写死 10ms
