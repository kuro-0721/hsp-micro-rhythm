【判读结论】
  1. REQ-101（帧间隔 p95 ≤ 33ms）达标：6 档 p95 均为 33ms，超时帧（>38ms）均为 0。
  2. **音符密度对 CPU 绘制影响很小**：从 0 个音符到 200 个音符（每轨 50），draw 仅由 2ms 增至 6ms。
     32 位双像素写（fb_clear / gfx_fill_rect）把整屏清屏 + 轨道线 + 判定线 + 200 个音符压到 6ms 以内，
     明显优于 M2 逐像素填充的 8ms。
  3. **主要开销是 flush（26~29ms），且与音符数量无关**——这是在等 VSYNC，不是 CPU 在计算。
     该时间段 CPU 空闲，可用于判定/触摸等独立线程。
  4. 由此推论：脏区更新能节省的只是 draw（上限约 5ms），无法缩短 flush；
     而 p95 恰好压在 33ms 目标线上，帧循环本身没有余量。

【局限（不美化）】
  1. 本测试是**合成音符密度扫描**，不是真实演奏场景；真实演奏（含判定、计分、UI 刷新）待第 3 步后复测。
  2. p95 = 33ms 恰好等于目标值，属于「刚好达标」，不能表述为「有余量」。
  3. 第一次抓取失败（脚本先打开串口、学生后拔插，导致句柄失效）；修正为容错重连后重抓，失败残留已保留。
  4. USB 重新枚举期间约丢失启动最前面的 1~2 行（重连延迟），但压力测试各档数据完整。
