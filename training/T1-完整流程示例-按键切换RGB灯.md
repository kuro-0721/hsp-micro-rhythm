# T1 完整流程示例：按键切换 RGB 灯

**目标**：用一个很小的产品功能，把“需求 → 设计 → 实现 → 测试 → 总结”完整走一遍，每一步都用到对应的模板、提交类型和证据。做完之后，你自己的产品项目就是把这个流程再走一遍。　**时长**：约 5～6 小时（可分 2～3 次完成）　**前置**：T0

## 示例功能

> 按下黄山派 KEY1，板载 RGB 灯切换到下一种颜色（红 → 绿 → 蓝 → 红……），并在串口打印当前颜色。

KEY1 接在引脚 34、高电平有效（见 SDK 板型配置 `customer/boards/sf32lb52-lchspi-ulp/hcpu/board.conf`；`BSP_KEY1_PIN` 宏是否存在请让 agent 先到 SDK 里确认）。RGB 灯的驱动已在 `src/main.c` 里用过。

## 流程总览

| 阶段 | 你做什么 | agent 做什么 | 模板 | 提交类型 | 主要产出 |
|---|---|---|---|---|---|
| 0 准备 | 建分支 | — | — | — | 分支 |
| 1 需求 | 写 REQ 和验收标准 | 帮你检查“能不能验证” | `docs/01` | `docs(prd)` | REQ-001/002 |
| 2 设计 | 画图、做一个二选一决策 | 提供备选与权衡 | `docs/02`、`docs/adr/` | `docs(design)` | 设计与 ADR |
| 3 实现 | 审计划、把关代码 | 实现并编译 | `src/` | `feat(key)` | 可编译的代码 |
| 4 测试 | 上板验证、留证据 | **暂停等你的证据**，再分析 | `docs/03`、`docs/04`、`evidence/` | `docs(test)`、`hw(key)`、`fix(key)` | 测试计划、证据、报告 |
| 5 总结 | 写研制总结 | 帮你核对数据 | `docs/05` Word | `docs(summary)` | 研制总结 |
| 6 收尾 | 检查、打标签 | — | `manifest.yaml` | `docs(manifest)` | 标签 `T1-done` |

每个阶段都要小步提交，当天写开发日志，`AI协作:` 如实填写。

## 阶段 0：准备

1. `git switch -c feat/t1-key-rgb`
2. 让 agent 先复述规则（`docs/guides/agent-collaboration.md` 第 2 节），确认它知道“上板结果要暂停等证据”。

## 阶段 1：需求（约 0.7h）

1. 打开 `docs/01-需求规格说明.md`，把第 3 节里的**示例行替换成你的需求**（不要新增一堆空行）：
   - `REQ-001`：按下 KEY1 后 RGB 灯切换到下一种颜色，顺序为红→绿→蓝循环。
   - `REQ-002`：**一次按下只切换一次**颜色。
   每条要有可验证的验收标准，例如“连续按 10 次，颜色按顺序切换 10 次，无重复、无遗漏”。
2. 非功能需求（第 4 节 REQ-101～104）暂时保留模板示例，或按你的理解改写。
3. 让 agent 检查：“这条验收标准别人照着能判定通过/不通过吗？”把它指出的问题和你的取舍写进日志。
4. 提交：`docs(prd)`。

## 阶段 2：设计（约 1h）

1. 在 `docs/02-方案设计说明.md` 填写：模块划分（按键采样、颜色状态、RGB 输出）、流程图或时序图（Mermaid 即可）、第 11 节“需求—设计追踪”（REQ-001/002 对应哪个模块）。
2. **做一个决策并写 ADR**：按键怎么读？
   - A 周期轮询线程（例如每 5ms `rt_pin_read`）
   - B GPIO 中断
   让 agent 给出两种方案的权衡，**你自己选**，写 `docs/adr/0001-*.md`（用 `0000-template.md`），同步 `docs/02` 的决策表。
3. **本示例第一版刻意先做最简单的方案**：只检测电平变化触发切换，**不加消抖**。这样 REQ-002 会在测试阶段真正被检验。（实际产品不要故意省略，这里是为了让你亲历“测试发现问题”。）
4. 在 `docs/02` 第 10 节“物理验证计划”写下需要上板验证的点。
5. 运行 `python scripts/check_trace.py`，修到无报错。提交：`docs(design)`（ADR 可单独提交）。

## 阶段 3：实现（约 1.2h）

1. 让 agent 按提示词 6.3（`docs/guides/agent-collaboration.md`）下达任务，并要求：先读 `docs/01`、`docs/02`、`src/main.c` 和 SDK 里相关例程，**先给计划**；不要凭记忆写 SDK API，用到的函数宏要说明来自哪个头文件。
2. 你审计划，再让它实现。新代码放 `src/`（可新增 `key.c/.h`，`src/SConscript` 会自动收集）。
3. `python scripts/build_firmware.py` 编译，直到通过。
4. **把关清单**（写进日志）：
   - `git diff` 没有动 `project/` 下的构建文件和 `proj.conf`（若动了，agent 要说明每项的依据）
   - 用到的 SDK 函数和宏，你自己 `grep` 过确实存在
   - 实现与设计文档一致（轮询还是中断？周期多少？）
   - 没有越界功能（比如 agent 擅自加了消抖或长按——如果加了，要么否决，要么回头改文档，不能悄悄接受）
5. 提交：`feat(key)`，`验证:` 写“编译通过”和命令输出摘要，`AI协作:` 如实。
6. **编译通过就停下来**——agent 不知道灯到底有没有按预期切换。

## 阶段 4：测试（约 1.3h）

1. **测试用例**（可在实现之前写，也必须在上板之前写好）：`docs/03` 的用例表替换为：
   - `TC-001`（物理，关联 REQ-001）：连续按 10 次，观察颜色顺序与串口日志
   - `TC-002`（物理，关联 REQ-002）：连续按 20 次，包括快按和用力按，统计颜色切换次数是否等于按键次数
   - `TC-003`（集成，可选）：编译通过，输出摘要入证据
   写明前置条件、步骤、预期结果、证据要求。提交：`docs(test)`。
2. **上板验证**：烧录后按 TC 执行，证据存 `evidence/T1/`：
   - 串口日志原文（每次切换一行，带时间戳最佳）
   - 一段视频或照片（大文件放网盘，在 `evidence/` 里放链接说明）
   - 把按键次数（你自己数的）写在日志文件开头，与切换次数对照
3. 把证据交给 agent 分析，**核对它的结论是否被证据真正支持**（日志里确有它说的那几行吗？）。
4. **如实记录结果**：
   - 若 TC-002 出现“按一次跳多次”：在 `docs/06` 的“问题与缺陷”登记 `B-001`；让 agent 排查并修复（加消抖是常见办法，但要改文档：先更新 `docs/02`，必要时补 ADR，再改代码）；提交 `fix(key)`；**保留失败日志**，重测后另存一份，在 `docs/04` 的“回归测试记录”里写清“失败→通过”。
   - 若按 20 次都没问题：不要编造问题。再按 30 次，仍无问题就在报告里写“未复现”，并在“遗留问题与已知局限”里写明：未做消抖，存在风险。可选做：加入消抖作为加固。
5. 填写 `docs/04-测试报告.md`：用例执行结果、缺陷汇总、需求覆盖矩阵（REQ-001/002，以及保留的非功能需求行）。
6. 提交：`hw(key)`（证据）、`fix(key)`（如有）、`docs(test)`（报告）。

> **没有开发板**：做到编译通过；TC-001/002 在报告里标“未执行：无开发板”（不得标“通过”），`manifest.yaml` 的 `known_issues` 登记，并把补做计划写进 `docs/06`。这不扣分；编造现象或日志按学术诚信处理。

## 阶段 5：总结（约 0.8h）

打开 `docs/05-研制总结.docx`（Word）。本示例只需填写下面这些章节，其余章节保留模板，不用填：

| 章节 | 填什么 |
|---|---|
| 1.1 / 1.2 | 项目背景、功能一句话 |
| 3.1 | 需求验收结果：REQ-001/002 是否满足，对应证据 |
| 5.1 / 5.2 | 测试概况、物理验证结果（引用 `docs/04` 和 `evidence/T1/`，数字要一致） |
| 6.1～6.4 | 用的工具和模型、人与 agent 分工、**一个典型案例复盘**（agent 出错或你否决了它什么） |
| 9.2 | 做得不好、需要改进的地方 |

写完后让 agent **核对数字**（提交数、用例数、通过数是否与 `git log`、`docs/04` 一致），但文字请自己写。提交：`docs(summary)`。

## 阶段 6：收尾

1. 填写 `manifest.yaml` 中本示例相关的部分（`submission`、`dev_agent`、`physical_verification` 至少 1 条、`known_issues`），运行 `python scripts/check_manifest.py`，把“必须补全”中与本示例有关的项清零（产品相关的字段可保留）。
2. `python scripts/check_all.py`，把输出贴进日志。
3. 合并并打标签：
   ```bash
   git switch main
   git merge --no-ff feat/t1-key-rgb
   git tag -a T1-done -m "T1 完整流程示例完成"
   ```
4. 在 `progress.md` 登记 T1。
